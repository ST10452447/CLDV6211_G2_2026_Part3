1. Full feature list of the application
My EventEase app has grown quite a bit from part one to part three. At the start it was just simple crud for venues, events and bookings with placeholder image urls. In part two I added actual image uploads using the local azurite emulator, also double booking prevention and a consolidated bookings view that lets you search by booking id or event name. For part three I had to implement advanced filtering and then migrate everything to the real cloud.
The advanced filtering part lets a booking specialist filter events by three things at the same time: event type (like conference, wedding, concert), date range (start and end date) and venue availability. I made a separate lookup table called EventTypes so the data is normalised and easy to extend later. The search page uses a viewmodel that holds the filter criteria and the results, and all three filters work together – for example you can search for “conference” events happening in june that still have free venues. The ui is clean with bootstrap cards and a dropdown for event types.
The basic crud functions are still there – you can add, edit, delete venues and events, and create bookings. The delete method checks if a venue or event has any active bookings before it lets you delete, so no data integrity problems. The bookings index page from part two shows venue and event details together, plus a search box that filters by booking id or event name. For images, they upload to azurite in part two but for part three I changed the connection string to point to a real azure storage account (Microsoft Azure, 2024a).
2. Azure services used and why
For part three I used three main azure services: Azure SQL Database, Azure Storage Account (blob storage) and Azure App Service. I also used the free student subscription with 100 dollar credit (Microsoft, 2024).
I chose Azure SQL Database because it is a platform as a service (paas) database. Microsoft handles backups, patching and high availability for me. I don’t have to manage a virtual machine or install sql server myself. It also supports the same t-sql language as my localdb so migrating was easy using a bacpac file (Microsoft Learn, 2025a). For a real production system this is much better than running sql server on a vm because it scales automatically and you only pay for what you use.
For images I used Azure Storage Account specifically blob storage. Blob storage is cheap and perfect for storing images because you can serve them directly to the browser with a public url. In part two I used the azurite emulator which simulated the same api locally, so switching to the real storage account was just a matter of changing the connection string in my app settings (Microsoft Azure, 2024b). I also used the azure storage explorer tool to upload my existing images to the live container and to check that everything worked.
The web app itself is hosted on Azure App Service. This is also paas – I just publish my asp.net core mvc project from visual studio and azure takes care of the underlying windows server, iis and scaling. I chose the free f1 tier because it is enough for testing and doesn’t cost anything while I am learning (Microsoft Azure, 2024c). App service also let’s me override configuration settings like connection strings in the portal without redeploying the code – that was really helpfull when I needed to switch from localdb to azure sql.
3. The migration experience (from local to cloud)
Honestly the migration was a bit stressful at first but after I understood the steps it became easier. My local environment was using sql localdb for the database and azurite emulator for blob storage. To move to the cloud I had to migrate both.
For the database I used the export data-tier application wizard in sql server management studio. I right clicked my local EventEaseDB, chose tasks then export data-tier application, and saved it as a bacpac file (Microsoft Learn, 2025b). Then I created an azure sql database in the portal, and used the import data-tier application wizard to upload the bacpac. That copied all my tables – venues, events, bookings and eventtypes – plus all the sample data I had seeded. The only tricky part was the firewall rule on the azure sql server. At first my app couldn’t connect because I forgot to turn on “allow azure services to access the server”. Once I enabled that everything worked (Microsoft Azure, 2024d).
For the images I created a storage account and a container called venue-images. I set the public access level to blob so the images could be viewed directly in the browser. Then I used azure storage explorer to connect to my azure subscription and uploaded all the images that were previously in my local azurite container. This was straightforward because storage explorer works the same way for local emulator and real azure – I just had to switch the connection.
The configuration changes were mainly in my appsettings file. I created a separate appsettings.production.json file with the live connection strings for azure sql and azure storage. When I published the app to azure app service from visual studio, I also set the same connection strings in the portal under environment variables (Microsoft Azure, 2024c). That way the app running in the cloud reads the live database and storage, not my local ones.
Why is seperation of environments important? In professional development you never want to test new features on the live production database because you might break real user data. Having a local development environment (with azurite and localdb) let’s you experiment safely. Then when everything is tested you deploy to production with a clean migration. This also helps with team work – different developers can work on their own local copies without messing up each other’s work (Microsoft, 2024).
4. Technologies used and why
I used ASP.NET Core MVC because it gives a clear seperation between models, views and controllers. It also has built in dependency injection which made it easy to inject my blob storage service into the controllers. That saved me from writing all the sql manually.
For image uploads I used the azure storage blobs sdk for .net. The blob storage service class I wrote handles connecting to either the emulator or the real storage account based on the connection string (Microsoft Azure, 2024b). I also used bootstrap for the front end layout and icons to make the interface look professional even though I’m not a designer.

 
Theory: Advanced Cloud (Part 3 Questions)
Question 1: How does Cosmos DB differ from a traditional database?
Azure Cosmos DB is really different from a traditional sql database like sql server or mysql. The biggest difference is that traditional databases are relational and use a fixed schema – you have to define your tables and columns before you insert any data. If you want to add a new column later you have to run an alter table command which can lock the table for a long time if it has millions of rows (Miyamasu, 2025). Cosmos db is a nosql database, so it is schema agnostic. You can store documents that have different fields and it just works. For a booking system like eventease that could be useful if different events need different custom fields.
Another huge difference is scaling. A traditional database scales vertically – that means you buy a bigger server with more cpu and ram. There’s a limit to how big you can go. Cosmos db scales horizontally. You just add more partitions or more servers and the database automatically spreads the data across them (Microsoft Learn, 2025a). This is almost unlimited scaling and it’s built in. For a global event management company that suddenly gets popular in another country, cosmos db could automatically replicate the data to that region and serve users fast.
Cosmos db also offers multiple consistency models – strong, bounded staleness, session, consistent prefix, and eventual (Miyamasu, 2025). With a traditional sql database you usually get strong consistency only, which is safe but can be slow over long distances. With cosmos db you can choose session consistency for example, which guarantees that a user always sees their own writes but other users might see data a few milliseconds later. That’s often good enough for a booking system and much faster.
Traditional databases use sql as the query language. Cosmos db supports multiple apis – a sql-like api, mongodb api, cassandra api, gremlin for graphs and table api. That flexibility means you can migrate an existing mongodb app to cosmos db without rewriting all your queries (Microsoft Learn, 2025a). But for a brand new project like eventease, using the native core sql api is fine.
The last big difference is that cosmos db is fully managed and global out of the box. With a traditional database if you want multiple regions you have to set up replication yourself. Cosmos db let’s you turn on global distribution with a few clicks and you get automatic failover and low latency everywhere. Of course cosmos db is more expensive than a single small sql database for simple workloads, but for a truly global app it’s worth it.
Question 2: Key considerations when designing logic apps that handle sensitive data
If you are building logic apps that process personal information like customer names, emails or credit card numbers, you have to be really careful about security. The first thing is encryption. Azure logic apps automatically encrypt data at rest using 256 bit aes encryption – that’s the same standard used by governments (Microsoft Azure, 2024e). For data in transit, logic apps use tls (transport layer security) so that no one can sniff the data while it’s moving between services. For eventease that would be important if we used a logic app to send booking confirmations by email – the customer’s name and event details would be encrypted on the wire.
The second thing is access control. You should never give people more permissions than they need – that’s principle of least privelage. With azure rbac (role based access control) you can assign roles like logic app contributor or logic app operator (Microsoft Azure, 2024e). For example a support agent could be given operator role so they can see the run history and troubleshoot why a booking didn’t go through, but they cannot edit or delete the logic app itself. That prevents accidents or malicious changes.
The third and often overlooked thing is securing the run history. By default logic apps log every input and output of every action. If your logic app processes a booking that includes a customer’s email address, that email would appear in plain text in the logs (Microsoft Azure, 2024e). Anyone with access to the logic app’s run history could see it. That’s a big privacy risk. To fix this you can enable secure inputs and outputs on the trigger or actions that handle sensitive data. When that’s turned on, the logs show asterisks instead of the real data. The logic app can still use the data but it’s not stored in the logs. For eventease I would definitely enable that for any action that touches customer personal information.
Another consideration is using managed identities instead of connection strings with keys. A managed identity is basically a service account that azure automatically manages. You give that identity permission to access other resources like a storage account or a sql database, and you never have to store a password or key in your logic app (Microsoft Azure, 2024e). This is more secure because there’s no secret to leak. For eventease if a logic app needed to read from blob storage to attach an invoice pdf, using a managed identity would be safer than storing a storage account key.
Finally you should set up monitoring and alerts. If a logic app fails because someone tried to inject malicious data or because a service is down, you want to know immediately. Azure monitor can alert you when a logic app run fails. Also you should regularly audit who has access to the logic app using azure’s activity logs.
Question 3: How combining Event Grid with other services creates robust workflows
Azure event grid is like a messaging backbone for serverless applications. It’s a fully managed event routing service that takes events from sources and sends them to handlers. The really powerful thing is that you can combine event grid with azure functions, logic apps, automation accounts, and many other services to build workflows that are decoupled and resilient (Microsoft Azure, 2024f).
Here’s an example for eventease. Suppose every time a new booking is created, we want to do three things: generate a pdf invoice, update a customer loyalty system, and send a confirmation email. Without event grid, the booking controller would have to call each of these services synchronously. If the email service is down, the whole booking might fail or take a long time to time out. That’s a bad user experience.
With event grid, the booking controller just publishes a “BookingCreated” event to an event grid custom topic. That’s very fast and doesn’t depend on the other services being up. Then three separate event subscriptions are created – one for each handler (Microsoft Azure, 2024f). The first subscription sends the event to an azure function that generates the pdf. The second sends it to a logic app that updates the loyalty database. The third sends it to another azure function that sends the email. If the email function fails, event grid will automatically retry sending the event with exponential backoff (like 10 seconds, then 30 seconds, then 1 minute). If it still fails after 24 hours, the event is moved to a dead letter queue where you can inspect it later. The other handlers still run normally – they don’t get held up by the email failure.
This makes the workflow robust because the producer and consumers are decoupled. A failure in one consumer doesn’t affect the others or the main application. Also, event grid supports filtering. You could have different subscriptions for different event types – for example a “VIPBookingCreated” event could go to a different handler that sends a special thank you gift (Microsoft Azure, 2024f).
Another use case is image processing. When a user uploads an image to blob storage, a storage event can trigger an azure function that automatically creates a thumbnail and runs cognitive services to detect objects or generate tags. That’s perfect for a venue booking system where venues might upload gallery images – you could automatically tag them as “indoor”, “outdoor”, “seaside” etc.
Event grid also works with azure automation. If a virtual machine stops unexpectedly (that’s an event), event grid can trigger an automation runbook that restarts the vm. That’s self healing infrastructure.
So combining event grid with functions, logic apps and automation creates workflows that are event driven, loosely coupled, and have built in retry and dead letter handling. That’s the modern way to build reliable cloud applications.
